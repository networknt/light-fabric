# Configuration-layer pipeline integration (supported baseline)

The producer accepts an already fetched values/files directory. It does not fetch Config Server, start shared stacks, publish layers or call AWS. A real Config Server run was not performed: no endpoint/function-user was provided. Effective customer configurations are not included in local evidence.

1. The existing pipeline authenticates as the function user and materializes configuration with the existing light-runtime `prepare_config_with_provenance` producer into an owned temporary external directory. Keep that credential in the pipeline; do not copy it into the layer, arguments, logs or Portal records.
2. Pin the code ZIP/profile and validate the effective directory with that actual bootstrap. `build-config-layer.sh SOURCE OUT.zip --bootstrap PATH` copies input without modifying it, runs real offline Rust preparation/plan compilation, generates the root `light-lambda-layer.json` v1 manifest, revalidates its file hashes through Rust, and emits a deterministic ZIP. Source date is SOURCE_DATE_EPOCH or the source commit timestamp. Manifest files are stable sorted root-relative paths/SHA-256, effective configDigest and deterministic createdAt. Files stay at layer root so extraction mounts directly at `/opt`; there is no extra config/ or opt/ prefix.
3. Keep both validation report and code/layer SHA-256. An enabled Validator, Router rewrite rule or other unavailable profile is an admission failure, not a skipped handler. Offline validation starts no precision engine, loads no AWS credentials, performs no backend dispatch and does not prove remote targets/keys ready.
4. Validate both the package and layer before any later owner-controlled publication. The layer extractor requires an exact manifest/file set, regular files and safe paths. Rust Init checks the listed content digests; changed layer bytes reject Init. A manifest is an integrity/inventory record, not a signature or secret envelope.
5. The later deployment pipeline sequence is `PublishLayerVersion` -> `UpdateFunctionConfiguration` (pin the layer) -> `PublishVersion` -> `UpdateAlias`. None of those APIs were called here. Bind compatible immutable code and layer versions; do not update aliases on validation failure.
6. Report alias, function version, layer version/ARN, code ZIP SHA-256, layer ZIP SHA-256, configDigest, package profile, architecture/runtime, source HEAD plus dirty-source manifest identity, configured enabled handlers and preserved ALB target-group header mode to Portal through the existing authorized pipeline. This local tooling does not write Portal records.

The root directory layout is shared with the Java layer. It does not establish semantic parity, a safe binary-only swap, or an ALB header-mode migration. Retain each target group's multivalue-header mode and pin configuration compatibility per runtime. The baseline ZIP has exactly bootstrap; it carries no precision child, JRE, JAR or worker libraries. Workers, production limits, Validator activation and Router rewriting require their separate qualification/admission gates.
